## 2. Mechanism and derivation

**Pair.** The representation is R1: the x-key, with a stored y-bit, of the full <= m-fold signed sumset of a small base. Sigma is translation by base elements, plus the walked step R <- R + G. This is partial action (Class I), the recorded IC pair. Only the table arity changes.

**Generic splits and the vertex.** Take a j-sum table and enumerate the other m - j summands per attempt. Then:
- an attempt costs B^(m-j);
- the hit probability per attempt is about B^m/N;
- about B relations are needed;
- the table costs B^j to build, charged inside S.

The relation term is therefore N B^(1-j), and the total is N B^(1-j) + B^j + B^2. In exponents (B = N^beta) this is max(1 - beta(j-1), j beta, 2 beta). It is minimised at beta = 1/(2j-1), with value j/(2j-1).

j/(2j-1) decreases in j, so the best split at fixed m is j = m: 3/5, 4/7 and 5/9 at m = 3, 4, 5. Table B sits at (m, j) = (2, 2), exponent 2/3. The Rust mitm oracle at m = 3 uses a pair table plus one subtraction per target, so j = 2 and the exponent stays 2/3.

**Lower bound.** Proof: if beta <= 1/(2m-1), the first term is >= 1 - (m-1)/(2m-1) = m/(2m-1). Otherwise the second term m beta exceeds m/(2m-1). Also 2 beta <= m beta.

**Gap to rho.** m/(2m-1) - 1/2 = 1/(2(2m-1)), so the gap to rho grows like N^(1/10) at m = 3, where the incumbent's grows like N^(1/6).

**Why this is constant-level, stated against IDEA-20261024-a2b05d.**
- In a2b05d's model the recipe has per-attempt order k = 0, because each attempt is one lookup.
- The MITM corollary there (`mitm_never_sub_generic`, k >= m/2) is about the engine-default split. It does **not** cover this oracle. The brief's "k = ceil(m/2)" reading does not apply here.
- The free-oracle line there (`free_oracle`: k = 0 is sub-generic at m >= 4, exponent 2/(m+1)) also does not apply, because that model leaves memory uncharged.
- What keeps j = m above 1/2 is the B^m table built inside S. That is a2b05d section 8 (`MemoryCouplingArityTwo`: time2 >= 2/3 with mem2 = 2 beta) generalised from m = 2 to m. At m = 2 it compiles under plain `lean`, with machine_verified pending. For m >= 3 it is the derivation above, proposed as a Lean target in section 5.

The exponent claim is therefore: none, constant only.

**Constant model (qc3_fullsumset_model.py; unit GAE per sqrt(r), Table B's).**

```
S(B, m) = [ c_tab * sum_{j=2..m} K_j(B) + c_fb * B + c_w * rho_rel * B * r / (2 K_{<=m}(B)) ] / sqrt(r)
K_j(B)  = (1/2) sum_{k=1..j} C(B,k) C(j-1,k-1) 2^k     (signed multisets, folded by global negation)
c_tab = 1 GAE/key (H3), c_w = 1.096 GAE/trial (H3), c_fb = (13074.8 - 12432)/111 = 5.79 GAE/abscissa,
rho_rel in [0.667, 1.0] (H1), hit probability 2 K/r (H2), linear algebra negligible at B <= 64
```

## 5. Lean target (proposed, not written)

This generalises IDEA-20261024-a2b05d section 8 from m = 2 to the table-arity family. Proposed file: `formal/CryptoResearch/IC/TableVertexArity.lean`. Over the reals, with integers 2 <= j <= m and beta > 0:

1. `max (max (1 - beta*(j-1)) (j*beta)) (2*beta) >= j/(2*j-1)`, attained at beta = 1/(2j-1).
2. j/(2j-1) is strictly decreasing in j, so j = m is the best split at fixed m.
3. m/(2m-1) > 1/2 for every m >= 1: no member of the family is sub-generic once the table is charged.
4. Control: dropping the table term (memory uncharged) recovers a2b05d's k = 0 line 2/(m+1), which is < 1/2 at m >= 4. The table charge is load-bearing.

This proves the model's exponent statement only. The constants c_tab, c_w and rho_rel are not formalised.
