# DEVIATIONS (SA-16)

The frozen criterion text (exponent on controls < 0.6 with CI excluding 1, otherwise "uncalibrated"; prediction: all solvers <= 0.5) was **not changed**. The items below are operationalisations the pre-registration left open, and scope limits. Each is recorded so the reader can discount them.

1. **Meaning of "exponent".** The pre-registration does not say exponent of what in what. I used: exponent e in `CPU time per recovered decomposition ~ B^e`, i.e. log2( mean CPU time / recovery rate ) regressed on log2 B over the sweep points where recovery rate >= 50%, with a 95% bootstrap CI (2000 resamples of the per-trial times; recovery counts resampled binomially). Brute-force enumeration is e = 1 by construction (measured 1.01 [0.93, 1.08], so the harness resolves the criterion). A solver needs >= 5 such sweep points (>= 4 doublings; the sweeps use steps of 2 or 3 doublings) or the exponent is reported as "undefined".
2. **Added discrimination test.** Because polylog-cost lattice solvers have e ~ 0 wherever they succeed, including on generic instances below their reach, the exponent criterion alone cannot tell a calibrated solver from one that merely works at small B. I therefore also report reach (largest B with recovery >= 50%) on each control against the same solver on the matching generic null family, and call a solver "non-discriminating" if the gain is 0. This is an addition, not a replacement; the verdict line states which part of the criterion each solver fails.
3. **Solvers covered.** Ideas 1 and 2 solvers were run in the forms available here (LLL form lattice `L3`; level-(m,s) Coron-style bivariate Coppersmith on S_3; a 2-dimensional Gauss/Babai Vieta-plane solver as the Idea-2 analogue). Ideas 7 (integer programming) and 12 (learned shifts) have no solver in this repository snapshot, so they were NOT run; `run_sweep.py` has a dictionary `SOLVERS` where they can be added.
4. **Control-aware variants.** The raw solvers do not exploit degeneracy, so for controls (i) and (ii) I added variants that are told which control they are on: `biv_rad_*` (Coppersmith on the radical of S_3, using f(x_R)=0), `vieta_cvp`, `L2diag` and `cop_uni_*` (use x1 = x2). They are reported separately and are never counted as evidence for the raw solvers.
5. **Control (i) uses curves with ~p-size coefficients.** Making R a rational 2-torsion point and R = P1+P2 with small x1, x2 forces a ~ x1 x2 - xr(x1+x2) - 2 xr^2 mod p, which is of size p. There is no small-(a,b) version. The null family for (i) is therefore `Gp` (random ~p-size a, b), not the secp256k1-like `G`.
6. **Control (iii) curve.** Anomalous curves are y^2 = x^3 + b (CM by Z[(1+sqrt(-3))/2], p = (3u^2+1)/4, smallest b with #E = p, so a = 0 and b < 400), which keeps a, b small so L3 applies. Smart's attack needs a non-canonical lift (j = 0 curves lift canonically for every b, giving psi = 0), so the code lifts a as well as b.
7. **Primes.** p ~ 2^128 (main) and 2^96 (reach-scaling check), p = 3 mod 4 except in the first 128-bit control-(iii) run, where the prime was 1 mod 4 (slower sqrt, same results). Trials: 20 per cell at 128 bits, 12 at 96 bits, 5 for the enumeration baseline.
8. **Success for lattice solvers.** A returned (x1, x2) counts only if it passes the group-law check `verify_decomp` (x-coordinates of F_p points, x <= B, x(P1 +- P2) = x_R). The planted pair is never given to a solver. For bivariate Coppersmith the column `vanish` additionally records whether the two shortest reduced polynomials vanish at the planted root (an oracle-assisted necessary condition); the pass/fail analysis uses extraction success only.
9. **Bug found and fixed during the run.** The first `biv_rad_m2s0` results reduced g^k mod p before building the lattice (which destroys the mod p^k information) and recovered nothing. I fixed it, deleted the affected rows from `raw/C1_128.json` and `raw/C1_96.json`, and re-ran all `biv_rad_*` solvers (`raw/C1rad_128.json`, `raw/C1rad_96.json`). Raw `biv_m*` solvers on S_3 were never affected (powers of S are not reduced there). A `biv_rad_m3s0` solver was added at the same time.
10. **Control (iii) timing split.** The first run (`raw/smart_128_v1_unsplit.*`) timed the Smart logarithm and the table scan together, which hid the O(B) scan under the ~1 ms logarithm. It was re-run with the two timed separately (`raw/smart_128.*`, B up to 2^15; pair table only up to 2^10 for memory).
11. **Shared-host noise.** The host load average was 25-32 during the sweeps, so absolute CPU times (process_time) are inflated and noisy; only slopes and recovery rates are used.
