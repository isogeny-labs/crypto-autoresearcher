## Proposed identities, ownership and write-once artifacts

For one future, separately admitted task/session, let `A` be the accountable Coordinator authorizer, `T` the task and its receipt-owning agent, `S` that agent’s exact runtime session, `V` an independent verifier, and `W` the task’s actual worktree on its actual host. Let `Q` denote any required claim owner and epoch. **Every value is UNSET.** The serving model, effort, worktree, executable availability, host, device, mount and live owner are likewise unknown. No identifier is allocated here.

A future contract would give `T` one exclusive repository-relative scope under `coordination/goals/GOAL-ENDO-001/batches/{batch_id}/tasks/{task_id}/admission/`. Within it, distinct write-once artifacts would bind the published authorization reference; exact source and executable metadata; the literal command and literal and resolved `W`; raw stdout and stderr bytes; exit code; parsed emitter JSON or parse failure; the **complete** task-owned v2 `runtime-session-receipt.json`; and a seal containing each artifact’s byte hash and `T/S/Q` attribution. A separate exclusive verifier scope would hold `V`’s independently captured same-host comparison and verdict. A task receipt cannot be supplied by a caller, pasted from an earlier session, edited after sealing or substituted by the emitter’s JSON block. The exact paths, writer identities and no-overwrite mechanism require a future published contract; they do not exist by virtue of this draft.

The emitter is existing, host-dependent code. The complete receipt writer and exhaustive inherited-v1 grammar are **missing interfaces** in the inspected source. The independent comparison is a documented procedure, not evidence that a verifier has run. The composed J3 admission evaluator is also missing. `check_receipt_v3.py` cannot stand in for any of those components.

## Smallest prospective bootstrap rule and sequence

**Proposed normative text for future review, not a rule in force:**

> A Coordinator may authorize one named `receipt_bootstrap_only` administrative sequence for exactly one `T/S/W/Q` binding after publishing a scoped additive contract. The sequence may perform only the enumerated trusted-executable metadata checks, one exact emitter invocation, raw capture, construction and immutable sealing of `T`’s complete v2 receipt, and one separately owned independent same-host comparison. Each process and filesystem effect remains labeled by its actual effect, including `starts_process` and receipt writes. Only the bootstrap sequence may be evaluated without the receipt it creates. This exception yields **no J3 pass** and authorizes no target access, storage or bank materialization, schedule, dispatch, implementation, measurement, control execution or scientific run. Missing, mismatched, untrusted or unevaluable preconditions STOP the sequence; any failure after its first effect seals the failure record and STOPs. No implicit retry or widened command is permitted.

To become operative, that text would need an additive, source-pinned J3 applicability/authority contract and a Coordinator decision, with independent review, exclusive artifact paths, archival verification and publication. The future contract must say precisely how `receipt_bootstrap_only` relates to the presently closed action and dependent-action enums; an unknown action currently STOPs. It must also authorize the verifier’s otherwise host-effecting comparison commands within the same finite administrative boundary or separately before they run. This draft does neither.

**Pre-effect gate, before the first bootstrap process.** A future authorizer must be identified and empowered by that published contract; `T/S/W/Q`, the admitted task-native model and owner, exclusive scopes, exact C/P source hashes, intended command and a finite allowed-effect list must already be bound. The literal trusted executable paths, their resolved paths, bytes or SHA-256, UID/GID, mode, regular-file and executable status, and ancestor ownership/permissions must be established for the *actual* host before invoking them. The procedure names `/bin/sh`, `/bin/hostname`, `/bin/df`, `/bin/date`, `/usr/bin/sed`, `/usr/bin/awk`, `/usr/bin/tr` and `/usr/bin/tail`; system executable chains require root ownership and no group or world write (C emitter procedure, lines 9–20). No `PATH` substitution is allowed. If those paths are unavailable, an explicit port with new reviewable source bytes and pins is required; the historical `/Volumes/SSD990/...` path is never silently transplanted.

This pre-effect gate **must not demand the receipt that does not yet exist**. It must name an already authorized way to establish actual executable identity and availability without launching an unadmitted process. No such current host-control surface is established by the inspected bytes. If metadata collection itself would start the first process, the future contract must identify and authorize that exact first effect and its preexisting trust root; otherwise the gate is unevaluable and **STOP**. Unknown authorizer, owner, worktree, source hash, executable, write scope or task/session admission likewise STOPs before any bootstrap effect.

**Proposed ordered states:** `SOURCE_PINNED → AUTHORITY_PUBLISHED → PRE_EFFECT_BOUND → EMIT_CAPTURED → OWN_RECEIPT_SEALED → INDEPENDENTLY_COMPARED → LATER_J3_EVALUATED`. Every transition requires its own recorded inputs and a failure edge to `STOP`; reaching one state does not imply the next.

After the pre-effect gate, `T` would invoke only the exact reviewed command from cwd `W`, capture its exit status and unmodified stdout/stderr, and accept binding JSON only for exit zero and successful parse. The emitter’s `df -P .` must refer to that cwd. The receipt writer would assemble the complete inherited-v1-plus-v2 receipt from the captured bytes and exact task/session provenance, then seal it once. A failed command, malformed JSON, incomplete receipt or failed seal remains a failure artifact, never a hand-written replacement binding.

Only **after** that seal may `V`, in an independently admitted session on the same actual host, verify trusted command paths and capture `hostname` and `df -P W`. `V` compares the independently observed host, device and mount to the task-owned receipt after the finite, one-pass normalization. A v1 note-only receipt may be schema-parseable yet still STOP at this binding rule. The accepted threat limit is a trusted host, OS, runtime, loader and filesystem report: metadata, hash and same-host agreement do not prove binary authenticity or defeat a malicious host or self-attesting runtime (C emitter procedure, lines 56–66; C receipt schema, lines 69–96).
