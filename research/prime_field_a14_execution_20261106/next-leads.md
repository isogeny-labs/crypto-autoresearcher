## Concrete existing baseline gap

In [query_index.py](query_index.py), pair_construction loops over unordered
geometric pairs and all four sign combinations, executing a separate scalar
EC.add for each. Prepaid input signs already exist. For one ordinary pair A,B,
the four outputs are A+B, A-B, -(A-B), -(A+B). The two first coordinates share
the same nonzero x-denominator; negative output y-coordinates can be derived
with paid negation. Batch inversion can share inversion work across a bounded
set of pair denominators inside that base's construction. Preserve the four
original sign descriptors and insertion order exactly.

This is existing technique. Production
[_accel.py](../../src/crypto_autoresearcher/index_calculus/_accel.py) has
batch_inverse and subtract_many; [tails.py](../../src/crypto_autoresearcher/index_calculus/tails.py)
explicitly constructs F_a+S and F_a-S from one shared denominator and derives
negative tails. [harvest.py](../../src/crypto_autoresearcher/index_calculus/harvest.py)
uses _scan_np with shared signed slopes and a product-tree inverse. A12's
[batch_query.py](../prime_field_a12_execution_20261106/batch_query.py) already
executes a counted NumPy variant with paid padding/masks and exceptional scalar
fallbacks. Historical s3_solves/abstract scalar-equivalent counters in those
production callers are not A14 actual Fp measurements or runtime calibration.
No novelty, new symmetry or parity with all production optimizations is claimed.
